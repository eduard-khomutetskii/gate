Ralph run: card-stack slider implementation

Implemented per .omc/plans/card-stack-slider.md:
- index.html: headline, .stage (.avatar-badge, .card-stack with 4 .card, .dots nav)
- styles.css: dark-teal card look sampled from img.png (card bg #005561, page bg #004650,
  accent yellow #f4f350), pos-0..pos-3 stack classes (translateY/scale offsets), fixed
  aspect-ratio on .card-stack, 640px media query for mobile (columns stack, stack effect
  disabled on mobile since reference has no mobile treatment).
- script.js: 4 CARDS persona data objects (Руководителю [from reference], + 3 authored
  placeholders: Сотруднику/Бухгалтеру/Финансовому директору). Key design choice: since
  there are exactly 4 cards and 4 stack slots, content is rendered once per DOM element
  and never re-rendered — advancing the slider just rotates which physical element sits
  in which stack position (order array), avoiding any content-swap complexity.
  Transition uses Element.animate() (WAAPI) with Promise.all(anim.finished) — no CSS
  transitionend/timeout polling, avoiding the double-rAF timing hazard flagged in the plan.
  Only `transform` and `opacity` are keyframed. isAnimating guard prevents state desync
  from rapid clicking (verified via 8x rapid click test).
  goTo(targetIndex) computes rotation distance k and does ONE animation regardless of
  distance (accepted plan tradeoff, not per-step riffling).

Verified with Playwright (headless chromium, installed via npx for this session only,
not added as a project dependency — no package.json committed):
- 4 dots / 4 cards rendered, zero console errors on file:// load
- Clicking dots 1->2->3->4->1 updates front card text content correctly every time
- Rapid-click spam (8x) on one dot does not desync stack order (positions stay a clean
  0/1/2/3 permutation)
- Enter key on a focused dot advances the slider; aria-current/aria-label reflect state
- Visual screenshots match img.png layout closely (colors sampled programmatically from
  the reference PNG via PIL rather than eyeballed)

Fixed during verification: dot active-state indicator originally used a CSS `width`
transition (pill-shape widening) — this violated the "transform/opacity only" animation
criterion, so it was reimplemented as a fixed-width dot with a `::after` pseudo-element
scaled via `transform: scaleX()`.
